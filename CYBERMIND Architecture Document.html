CYBERMIND Architecture Document

Smart India Hackathon 2026 | Problem Statement SIH26153 | Predictive Cyber Defence Platform

1. System Overview

CYBERMIND is a four-tier, local-first platform that models a protected network as a sequence of host-communication graphs. A graph-temporal world model forecasts short-horizon attack risk, Parallel Futures compares defensive interventions in simulation, and the built-in local validator records bounded sandbox responses next to a frozen forecast. An optional Strix integration can test selected hypotheses and approved defences when its sandbox, CLI and provider are configured. Core forecasting runs locally, with no cloud model endpoint.

Observe → Forecast → Simulate → Validate → Defend → Re-test → Report

3. Ingestion and Graph Construction

The analyst selects a capture or flow CSV; no file is preloaded. Every event keeps its source identity (uploaded observation, dataset replay, synthetic scenario, controlled lab probe, blocked probe, validation record, approved action), so lab evidence is never presented as observed traffic. CSV columns are matched flexibly, and missing timestamps use a disclosed assumed interval. Raw PCAP flows stay Unassessed unless valid source labels exist.

Hosts are nodes and observed communications are directed edges. Features include packet and byte volume, rates, protocol and port information, duration, peer and port diversity, inter-arrival statistics and scanning patterns, depending on input coverage. Windows are 60 seconds with a 30-second stride, up to 64 retained states, and at least 3 are required to forecast. Training-only normalization statistics ship with the checkpoint.

If the checkpoint or its configuration is missing or invalid, forecasting is reported unavailable. The system never substitutes random or placeholder scores.

5. Strix Lab: Controlled Validation and Defence Re-test

Forecast -> bounded probe -> sandbox verdict -> proposed defence -> analyst approval -> same probe re-run -> blocked = mitigation evidence

When its isolated loopback sandbox (127.0.0.1:8081) is running, the Attack Lab can send bounded, non-destructive HTTP probes. Verdicts come from actual sandbox responses: succeeded, blocked (rate limit, WAF, authorization or structured block) or unreachable (no verdict asserted). The bundled demo's sandbox target may be offline; in that state no probe verdict is established. Probe activity is separate from model training.

When the sandbox confirms a vulnerability, the remediation layer proposes a patch or configuration change. The analyst reviews and applies it inside the lab, and the same probe runs again. A blocked response is direct evidence that the tested mitigation changed sandbox behaviour.

Local validation engine. Separately, the guaranteed offline path freezes the current forecast, calls four bounded endpoints on the bundled sandbox (health, invalid login, share access, query handling), stores HTTP status codes and SHA-256 hashes of response bodies, and links them to the forecast ID and model version.

Optional external Strix CLI. An adapter supports registered, authorized targets classified as SANDBOX, REPLAY or AUTHORIZED_TEST. Unregistered targets are rejected, autonomous runs are limited to SANDBOX, runs have timeouts and optional budgets, and findings are read from structured artifacts. It needs the Strix CLI, Docker and an LLM provider, so it is not part of the offline core. Stage hypotheses derived from findings are always marked inferred.

6. Analyst Layer and Counterfactual Simulation

The React Command Centre reads events, graphs, forecasts and validation records from the local FastAPI backend over REST and WebSocket. Parallel Futures copies the current graph, applies an in-memory intervention (isolate a host, block a port, restrict an edge, rate-limit), and reruns the same model against the no-action baseline. The recommender ranks results by predicted risk change, confidence proxy, reversibility and a collateral-impact heuristic. Outputs are model-based comparisons for analyst review, not measured causal effects and not executed firewall rules.

7. Protected Reporting and Deployment

Incident briefs are encrypted locally with AES-256-GCM using a fresh random 256-bit key and 96-bit nonce from Web Crypto. The JSON envelope holds format, version, nonce and ciphertext, never the key. The recipient imports it and supplies the separately shared key inside CYBERMIND; a wrong key or altered ciphertext fails decryption.

  • Windows: CYBERMIND.exe is a Docker-backed desktop launcher. It opens the React/FastAPI application in its own window and uses the pinned best.pt model inside the bundled image. Docker Desktop's Linux engine is required; CUDA and a cloud endpoint are not required for core inference.
  • Linux x86-64: the bundled image runs through Docker Engine and Compose on an ephemeral 127.0.0.1 port with a named volume and SHA-256 manifest. The launcher loads the image locally with no runtime pull.

9. End-to-End Flow

PCAP or CSV -> canonical flows -> temporal graph windows -> best.pt forecast -> Parallel Futures comparison -> local sandbox response check (optional Strix probe) -> encrypted incident brief -> in-app decryption

10. Operational Boundaries

  • Forecasts apply to aggregate graph windows, not to verified malicious hosts or flows.
  • Flow-triage bands are rule-based and are not best.pt output.
  • Rollout variance is an uncertainty proxy, not a calibrated confidence.
  • Parallel Futures is a model simulation, not proof of causal effect.
  • Strix probes are bounded, non-destructive and limited to the loopback sandbox unless an authorized target is registered.
  • A sandbox re-test shows the tested mitigation worked there; it does not prove production safety, and sandbox activity never retrains best.pt.
  • Consequential defensive actions remain under analyst control.
  • Production use would need security review, wider external validation, threshold calibration, key-exchange procedures and reviewed model updates.
